## 0. 主张先说清楚

用户问「怎样做比较好」。本方案的立场不是功能清单并列，而是一条可验证的产品路径：

**不要一上来做成全能办公机器人，也不要去做更弱的飞书 aily。先做工位上的专属萌宠秘书：会守、会收口、会记。**

品类钉死为 **专属办公秘书**。突出点对外只讲三个词：**专属、少扰、能记。** 形态上多两个词：**萌宠、飞书。** 机制上多两个词：**完成即归档、升级即解锁。**

一句话定位：

> **工位上的专属萌宠秘书：按你的目标和作息守着；飞书里帮你收口；你勾完成之后，把当天相关文档收成可回看的私人卡片。越用越像你的人，而不是越用越吵。**

桌面萌宠是形态，不是品类。对内可叫「秘书」；对外试点不要叫 EchoBot，以免被理解成情感陪聊。

面对「这不就是飞书 AI 吗」的标准回答：**aily 帮你做新的；我们帮你守节奏、记住你做完的。**

七条判断，后面所有分期都按此执行：

1. **第一印象必须是「每天想打开」，不是「又一个要配置的机器人」。** W0 的钩子是工位萌宠 + 今日目标卡；关注源与资讯晨报锁在 Lv3。顺序反了，产品会变成既吵又没用的通知机，或三周就腻的桌宠。
2. **不拼 aily，不拼陪聊。** 飞书 aily 已经占据「交付即用」：写文档、PPT、任务跟进、虚拟电脑、团队共享智能体。EchoBot 已经占据二次元陪聊。我们只占一格：桌面存在感 + 飞书收口 + 私人可审计记忆 + 硬配额少打扰。
3. **群消息提醒价值高、风险更高。** 权限、隐私、误报、打扰都会在第一周毁掉信任。锁在 Lv5，不是试点周的门面功能。
4. **陪伴不要做成卖萌闲聊。** 陪伴 = 守时窗。萌宠只驱动姿态和一句状态；飞书里仍是短卡片。皮肤不得改变推送配额与工作/兴趣隔离。
5. **内核是目标闭环，不是功能清单。** 设周/日目标 → 干活 → 勾选完成 → 秘书整理成卡 → 能力升级 → 下周更懂你。没有完成门闩和沉淀，推送永远是噪声。
6. **升级是能力门闩，不是养成数值。** Lv1 记目标 → Lv2 完成后整理 → Lv3 关注源晨报 → Lv4 文献/URL → Lv5 白名单群提醒。不能靠换皮跳级。
7. **本工作区不是从零开始。** EchoBot 提供 Decision / Roleplay / Agent 与 Live2D；VehicleMem / MemoryOS 提供记忆分层。试点把这些迁到办公秘书，而不是再造一套记忆中台，更不是在 EchoBot-main 里直接改出办公产品。

W0 只验证一件事：**目标 → 完成 → 整理 → 升到 Lv2。** 资讯晨报、文献、群监听、写 PPT、虚拟电脑，本周不做。

## 1. 研究背景与问题定义

### 1.1 为什么现在值得做

办公助手并不新。企业微信机器人、RSS、ChatGPT、Notion AI、信息流 App、各类 AI 伴侣，以及 2026 年的**飞书 aily（交付即用的 AI 同事）**都已经占位。现在值得做，不是因为「AI 更聪明了所以再做一个聊天窗」，更不是因为「我们会接飞书、别人不会」。值得做，是因为同时出现了三个可被产品化、而 aily / ChatGPT / EchoBot 都没有占住的缺口：

- **会答、会写，仍不会守。** ChatGPT 能回答「vLLM 最近改了什么」，aily 能在飞书里写完一份文档；它们都不会按你的作息、在正确的时间窗里、用硬配额提醒你，更不会把你**做完的事**沉淀成可审计的私人库。
- **平台记忆 ≠ 专属记忆。** aily 的上下文在飞书权限域里，偏向「公司里的我」；ChatGPT 的记忆在会话里，关了就散、难进内网。工位需要一份 edge / 私有 cloud 的 `MemoryItem`：工作与兴趣隔离、可删、可回溯原链。
- **工位需要存在感，但不能陪聊。** EchoBot 有 Live2D 日活钩子，缺工作语境与合规；IM 机器人有到达率，没有「深度工作时安静趴着」。缺的是双声道：桌面萌、飞书克制，同一套配额。

因此，本题不是「再做一个 Bot」，而是研究：**个人视角的持续秘书，能否在不打扰的前提下，让人真的愿意每天用；并在做完之后把文档收成自己的。**

### 1.2 AI 开发团队的真实痛点

以一个 8–15 人的 AI 开发小组为观察对象，一天里反复出现的不是「不会写代码」，而是下面五类损耗：

| 痛点 | 现场表现 | 现有工具为什么不够 |
|---|---|---|
| 信息过载 | 群、邮件、RSS、X、论文站同时响；真正相关的一条被淹没 | IM 没有个人相关性过滤；RSS 没有工作语境 |
| 技术跟进失败 | 关注的框架发了 breaking change，一周后踩坑才知道 | Changelog 要自己巡；ChatGPT 不会值守 |
| 群消息错过 | 「下午 3 点对一下评测集」被晚到的会议消息顶掉 | 群机器人广播，不判断「和我有关」 |
| 知识散落 | 好论文、好 issue、好发布会纪要进了收藏夹就再也找不到 | 收藏不等于结构化；聊天记录不可检索复用 |
| 工具多但不成体系 | Copilot 写代码、Notion 记笔记、RSS 看资讯、群里对进度 | 没有一条「感知→理解→行动→反馈→沉淀」的个人链路 |

这些痛点有先后。用户可以忍受「群里偶尔漏一条」，但很难忍受「每天被推 20 条无关摘要」。所以产品必须先解决**相关性与节奏**，再解决**覆盖面**。

### 1.3 现有形态对比与缺口

| 形态 | 它擅长 | 它缺什么 |
|---|---|---|
| 飞书 aily / 豆包工作伙伴 | 飞书内交付即用：写文档、PPT、任务跟进、虚拟电脑、团队共享智能体 | 平台记忆不是私人可审计库；主动跟进容易吵；没有工位存在感与硬配额；**生产新文档 ≠ 归档你做完的** |
| 企业微信 / 飞书 / 钉钉机器人 | 通知到达、审批、群广播 | 没有个人视角；默认吵；几乎不沉淀 |
| RSS / 邮件订阅 | 源可控、可回溯 | 无画像、无工作语境、无陪伴、无「点赞进库」 |
| ChatGPT / 内部 Chatbot | 问答与草稿 | 被动；无值守；无个人信息流；会话一关知识就散 |
| Notion AI / 文档助手 | 已有文档上的改写与检索 | 不会主动巡源；不会管节奏 |
| EchoBot / AI 伴侣 | 人格、陪伴感、日活钩子 | 缺工作语境；知识不可审计；难进企业合规 |
| 信息流 App（机器之心、X、即刻） | 兴趣吸引、发布会热度 | 不是为「你这个项目」服务；无法沉淀为个人知识库 |
| Jira / 飞书任务 / 日历 | 项目管理、截止日期 | 不是秘书；催办会毁掉少打扰 |

缺口可以收成一句话：

> **缺一个同时具备「个人视角 + 持续陪伴 + 工作语境 + 可沉淀」的产品。**

四者缺一不可。只有个人视角会做成第三个资讯 App；只有陪伴会做成办公版 EchoBot；只有工作语境会做成更弱的 aily 或冷冰冰的监控脚本；只有沉淀会做成没人愿意往里填的第二个 Notion。

差别不能写成「我们会接飞书、别人不会」。真正不一样、缺一就不成立的五条：

1. **专属记忆，不是平台记忆。** VehicleMem `MemoryItem` + 短/中/长期；工作 / 兴趣 / 作息 / 事实拆开；默认 edge 或私有 cloud。
2. **少打扰是产品，不是设置项。** 工作日主动出口写死：上班 1、下班 1、兴趣 0–1。多推一条算失败。
3. **双声道：萌是外壳，秘书是作业。** EchoBot 三层：Roleplay 只驱动桌面；Agent 才碰飞书、目标、记忆。
4. **完成才沉淀，不是自动建库。** 勾选完成 + 归档确认，才把授权文档 / 用户丢来的链接收成卡片。aily 生产；我们归档。
5. **升级是能力门闩，不是养成数值。** Lv3 才开关注源，Lv5 才开群提醒。不能跳级。

### 1.4 与本工作区现有资产对齐

快速浏览 `D:\agent memory\code` 后的结论：**没有办公助手、EchoBot 或产品文档可继承；不能假装从零发明记忆层。**

应直接复用、而不是重写的能力：

| 现有资产 | 可迁移到本产品的部分 | 迁移时必须改的地方 |
|---|---|---|
| **VehicleMem**（`VehicleMem/`） | `MemoryItem` 统一记忆条目；`ProfileUpdate(preferences / facts / knowledge)`；`add / search / update / delete / history`；edge / cloud / hybrid 三模式 | 车载画像把通勤、兴趣、偏好写在同一份 profile 里。办公场景必须拆成**工作画像**与**兴趣画像**，否则发布会内容会打进晨会简报 |
| **MemoryOS** | 短期滚动窗口 → 中期向量检索 → 长期画像；热度与更新策略 | 短期对应「今日对话与推送反馈」；中期对应「本周有用卡片」；长期对应「个人知识库 + 双画像」 |
| **mem0** | 记忆增删改查、反馈机制、私有化部署选项 | 反馈要从「对话是否记住」扩展为「推送是否有用 / 是否进库」 |
| **graphiti** | 实体与关系图，适合后期团队知识库 | 阶段 A/B 不做图；阶段 C 若团队库规模上来，再用图表达「论文–框架–项目」关系 |
| **车载 POC**（memoryos-chery 等） | 「陪伴 + 画像 + 记忆分层」的交互经验 | 办公陪伴是节奏管理，不是车机闲聊；禁止把车载人设直接套到工位上 |
| **EchoBot**（`EchoBot-main/`） | Decision / Roleplay / Agent 三层；Live2D 桌面宠；cron；BaseChannel | 不在上游仓库改办公逻辑；不用 ReMeLight 当办公记忆；不用 QQ/Telegram 当主通道；Roleplay 禁止碰工具 |

研究意义也在这里：工作区已经能「记住用户」，但还没有验证「记住之后，在办公节奏里主动推、少打扰、能沉淀」是否成立。本项目是记忆研究的产品化命题，不是旁路 Demo。

## 2. 产品主张与定位

### 2.1 一句话定位

**工位上的专属萌宠秘书：按你的目标和作息守着；飞书里帮你收口；完成后把文档收成你的私人卡片。**

内部代号：**「秘书」**。对外试点名可用「工位助理」。**禁止**对外叫 EchoBot。桌面萌宠是形态，不是品类。

### 2.2 不是什么（边界）

明确不做、或本阶段不做的事。W0 尤其不得以「用户提了」为由打开下表任何一项：

| 不是 | 对手已经更好 / 为什么不做 | 用户若要求时怎么回 |
|---|---|---|
| 更强的飞书 aily | 写 PPT、虚拟电脑、长时任务、团队共享智能体是官方的主场；去拼永远落后且更吵 | 「他们帮你做新的；我帮你守节奏、记住你做完的」 |
| 第二个企业 IM | 群是输入，不是产品本身；做群管理会立刻卷入权限与治理 | 「我只提醒和你相关的事，不管群」 |
| 第二个资讯 App | 信息流没有工作语境，留存靠刷，不靠用 | 「只推你关注的，默认每天就几条；关注源在 Lv3」 |
| 第二个通用 Chatbot | 问答是深度通道，不是首页 | 「复杂问题你来问；日常我值守」 |
| 待办 / 项目管理 | Jira、飞书任务、日历已经更好；管待办会把试点拖死 | 「周目标最多 3、日目标最多 3。完成是为了归档，不是管项目」 |
| 写 PPT / 虚拟电脑 / 浏览器代操作 | aily 专业版主场 | 「这类请用飞书 aily；我只在你勾完成后整理」 |
| 自动建库 / 未完成就归档 | 知识库会变成垃圾堆 | 「没勾完成、你没点确认，我不会入库」 |
| 群监听 / 客户端 hook | 合规红线；锁在 Lv5 且仅官方 Bot API | 「群提醒还没开。开了也只走白名单 + 官方 API」 |
| 情感陪聊 / 人设偶像 | 办公场景里卖萌闲聊会迅速掉信任 | 「工位上我可以可爱地坐着，但不陪聊」 |
| 未授权爬取 / 把内部文档送公网 | 合规与研究伦理红线 | 只走官方 Bot API 与用户授权源；公司场景默认私有化模型 |

### 2.3 目标用户画像：AI 开发团队的一天

试点用户不是「全体知识工作者」，而是下面这类人。后续推广到全部门时，只换关注源模板，不换产品内核。

**角色组合（第一期 5–15 人）：**

- 算法 / 研究员：盯论文、复现、评测集
- 工程：推理框架、训练平台、Agent 运行时
- 应用开发：把模型接到业务，关心 API、延迟、产品发布

**一天（用于设计推送时窗，不是文学描写）：**

| 时段 | 真实状态 | 秘书该做什么 | 秘书不该做什么 |
|---|---|---|---|
| 09:00–09:20 上班 | 开电脑、扫群、决定今天攻哪块 | W0：一条今日目标卡（从周目标拆，最多 3 条）。Lv3 起才叠加关注源晨报 | 十条资讯、问候散文、昨日闲聊回顾 |
| 09:30–12:00 深度工作 | 写代码 / 跑实验，讨厌打断 | 默认静音；只允许「breaking change / 安全 / 今天截止」 | 发布会花絮、趣味科技 |
| 12:00–13:30 午休 | 可以看长一点的东西 | 可选 1 条兴趣向：发布会、评测、行业长文 | 工作催办 |
| 14:00–18:00 会议 + 继续做 | 上下文频繁切换 | 会前 5 分钟只提醒「和你有关」；会后不复盘群聊 | 把群消息原文转发到私聊 |
| 18:30 下班 | 想关掉工作，又怕漏事 | 一条收工：今天点过赞的 0–3 张卡片 + 明天唯一必须看的一件 | 「加班加油」或闲聊挽留 |
| 20:00 以后 | 休闲或家庭时间 | 兴趣内容才允许展开；工作源进「明早」 | 工作提醒（用户显式关掉「夜间工作」之前） |

这个作息表就是陪伴的产品定义：**陪伴 = 守时窗，不是陪说话。**

### 2.4 设计原则

1. **少打扰。** 工作日主动推送默认上限：晨报 1、收工 1、兴趣 0–1、突发事件 0–1。超过即失败，不是勤奋。
2. **可解释。** 每条推送必须能回答「为什么此刻推给我」：因为你关注了 X / 你点赞过类似 Y / 你这周在做 Z。说不清就不推。
3. **可回溯原链接。** 摘要再好也不能替代原文。卡片必带原链；禁止只给模型改写、不给出处。
4. **用户掌控。** 关注清单、免打扰、工作/兴趣开关、进库与否、删除记忆，全部用户可见可改。画像不是黑盒标签云。
5. **先个人后团队。** 第一期只服务「我」。团队库是个人库的可选分享，不是默认同步。
6. **完成才归档。** 未勾完成、用户未确认，禁止整理文档入库。无 `source_url` 不准成卡。
7. **升级不跳级。** 关注源锁 Lv3，群提醒锁 Lv5。皮肤可换，能力必须靠门闩。

### 2.5 升级路径（能力开关）

| 等级 | 解锁条件 | 新能力 | 桌面宠变化 |
|---|---|---|---|
| Lv1 实习生 | 安装完成 | 记周/日目标；上班目标卡、下班收口各 1 条 | 会坐、会安静，完成时点头 |
| Lv2 助理 | 完整 1 周 + 至少 3 次完成→成卡 | 完成后整理授权文档；周五归档；撤销入库 | 多一个「整理中」姿态 |
| Lv3 研究秘书 | Lv2 且用户打开关注开关，有用率过线 | 关注清单 + 工作晨报（原阶段 A） | 晨报时挥手，仍不闲聊 |
| Lv4 知识管家 | 个人库周复用 ≥ 25% | 文献推送、指定 URL 监测 | 可切换皮肤，配额不变 |
| Lv5 机要 | 安全评审通过 + 群白名单 | 白名单群相关提醒 | 无新打扰动作；只在收工提示盒子 |

W0 的唯一升级目标是 **Lv1 → Lv2**。升级演出只允许出现在收工窗口，不得打断深度工作。

## 3. 价值飞轮（产品逻辑主线）

三层价值必须按顺序转起来。并列做，飞轮转不动。

```
吸引层（让人每天想打开）
    科技 / 发布会 / 关注的产品与技术动态
            ↓ 产生「有用 / 无用」反馈
提效层（让人愿意留下）
    文献、指定网站监控、上下班节奏、（后期）群提醒
            ↓ 点赞 / 收藏 / 纠正
沉淀层（让人离不开）
    个人知识库卡片 → 反哺推荐与问答 → 可选分享到团队库
            ↓ 推荐更准、更少打扰
        回到吸引层，质量上升
```

### 3.1 吸引层：为什么先做兴趣与关注动态

AI 开发者对「又一个效率工具」普遍过敏，但对「我盯的模型发了新版本 / 发布会有关键信息」不过敏。吸引层的任务不是娱乐，而是：

- 用**用户自己选的关注清单**证明「它懂我关心什么」；
- 用**每天固定、条数极少**证明「它不添乱」；
- 用**有用/无用按钮**开始收集画像，而不是先填 20 道问卷。

成功标准不是点击率最大化，而是：**种子用户第二天还想看晨报。**

### 3.2 提效层：为什么第二步才加文献与网站习惯爬取

文献检索和网站监控都需要画像已经有一点形状。冷启动时乱推论文，有用率会低于 20%，用户会判定「还不如我自己刷 ArXiv」。

提效层建立在吸引层的反馈上：

- 工作画像里已经有技术栈、当前项目关键词、常点的标签；
- 这时推「和你这周评测任务相关的 1 篇」，才像秘书，不像推销。

群提醒也属于提效层的最右端（实际放到 P2），因为它还依赖信任与合规，不只依赖画像。

### 3.3 沉淀层：为什么知识库是壁垒而不是第一周功能

第一周就做「自动知识库」会变成垃圾堆：模型乱分类、用户懒得清理、检索比收藏夹还差。正确做法是：

- 进库门闩默认是**用户点赞或手动收藏**；
- 高置信自动入库只作为后期实验，且必须可撤销；
- 卡片结构从第一天就按可检索设计（见第 7 节），但**入库动作后置**。

壁垒来自时间：用了 8 周的个人库，换任何 Chatbot 都补不回来。这是相对 ChatGPT 和资讯 App 的唯一不可复制资产。

### 3.4 为什么这个顺序能让人「喜欢用」

「喜欢用」在办公场景里不是快感，是三种连续体验：

1. **早上 30 秒有收获**（吸引）；
2. **白天没有被坑、没有被吵**（提效 + 节奏）；
3. **周五能看到自己这周到底吸收了什么**（沉淀）。

任何把 3 提前到 1、或把群提醒塞进 1 的方案，都会在试点第 2 周出现「免打扰被打开且不再关上」。

## 4. 核心场景与功能设计

用户原始 6 点需求全部覆盖，但**不并列同等重要**。下表是总编排，随后按场景写清规格。

| 优先级 | 原始需求 | 产品落点 | 阶段 |
|---|---|---|---|
| P0 / W0 | 周目标 + 日目标 + 完成后整理文档 + 升级 | 极窄目标（各 ≤ 3）→ 完成门闩 → 成卡 → Lv2 | W0 |
| P0 | 4. 陪伴，提醒上下班 | 目标卡占用晨报/收工配额，非闲聊 | W0 / A |
| P0 | 2 的前半：用户交互，提取画像 | 完成 / 改目标 / 归档确认 | W0 |
| P0 | 3. 休闲时间推送感兴趣内容（科技 / 发布会） | 兴趣频道；**锁 Lv3** | A |
| P0 | 6. 关注产品或技术，更新后主动提醒 | 个人关注清单 + 更新监测；**锁 Lv3** | A |
| P1 | 2 的后半：查找工作相关文献并推送 | 结合工作画像的文献推荐；**锁 Lv4** | B |
| P1 | 5. 指定网站更新推送；习惯爬取；点赞沉淀知识库 | 习惯源 + 知识库卡片；**锁 Lv4** | B |
| P2 | 1. 读取群消息然后定时提醒 | 白名单群 + 相关度提醒；**锁 Lv5** | C |
| P2 | 1 的延伸：会议 / deadline 抽取 | 从已授权消息抽任务 | C |
| P2 | 5 的延伸：团队知识库 | 个人库可选分享 | C |

### 4.0 场景 W0｜周/日目标、完成即归档、升到 Lv2（本周唯一 P0）

**用户故事。** 周一我设本周最多 3 条目标。每天早上飞书里只有今日目标卡。我勾「完成」之后，秘书把当天相关的授权飞书文档或我丢给它的链接收成 1–3 张预览卡，我点确认才入库。周五若本周目标勾完且至少 3 次成卡，秘书从实习生升到助理。

**触发条件。** 用户设定或拆解目标；用户点完成；用户确认归档。未完成不整理。

**输入。** 周目标标题、日目标标题、可选关联链接、上下班时间。

**输出形态。**

- 上班：今日目标卡，按钮「完成 / 改一下 / 明天」。占用晨报配额，不另开催办通道。
- 完成：归档预览卡「将归档这 1–3 份」，带原链与归属目标。确认才入库。
- 收工：未完成只问一次；不道德绑架加班。
- 周五：本周卡片索引 + 升级（若达标）。升级只在收工窗口。

**成功标准。** 完成→成卡 ≥ 3；撤销率 < 30%；工作时零弹窗；自己愿意下周继续。

**打扰控制。** 周 ≤ 3、日 ≤ 3。主动推送仍是上班 1 + 下班 1。目标催办不得第三通道。

**失败降级。** 没有可归档材料就说「这条没有原链，要不要丢给我一个链接」；禁止空摘要入库。整理错了可一键撤销。

**明确不做。** 不写 PPT、不虚拟电脑、不接 Jira、不读群、不自动建库、不把兴趣内容写进工作归档。

### 4.1 场景 A｜个人关注清单与更新提醒（原始需求 6，P0）

**用户故事。** 我是推理引擎开发，关注了 vLLM、SGLang、某个云厂商的推理产品。新版本或 breaking change 出来后，当天上班就能在私聊看到 3 行摘要和原链，而不是周末才在群里听说。

**触发条件。** 用户维护关注清单（产品 / 技术 / 仓库 / 博客）。监测源出现「版本、API、价格、停服、安全、评测第一名变更」等变更类型。工作时段合并进晨报；休闲时段允许单条插入。

**输入。** 关注对象名称、官方源 URL 或仓库、用户标注的「为什么关心」（可选，冷启动很有用）。

**输出形态。** 飞书交互卡片：标题、3–5 行摘要、变更类型标签、原链、一句「为何推：你关注了 vLLM」、按钮「有用 / 无用 / 稍后」。

**成功标准。** 关注源真实更新后，24 小时内送达率 ≥ 95%；用户判定「和我关注的是同一对象」≥ 80%；误报（把无关博客当版本更新）≤ 15%。

**打扰控制。** 同一源一天最多 1 条；多源合并进晨报，不连发。用户可设「只看 breaking / 安全」。

**失败降级。** 抓不到正文就只推标题 + 原链 + 「未生成摘要」；模型不确定是否 breaking 时标「待确认」，不要吓用户。

### 4.2 场景 B｜兴趣推送：科技与发布会（原始需求 3，P0）

**用户故事。** 中午或晚上我想看发布会和科技进展；上班时间只允许极短提示，避免我点进去看完 Keynote。

**触发条件。** 兴趣源更新，且当前时窗为「休闲」或用户主动问「有什么好看的」。工作时间仅当事件被标为「行业重大」（如Frontier模型发布、关键开源协议变更）才允许 1 条精简。

**输入。** 兴趣画像（点赞过的发布会、媒体、主题）+ 默认兴趣源。

**输出形态。** 工作精简：1 句 + 原链。休闲展开：结构摘要（发了什么、和我关注的技术有无交集、值不值得看原文）。

**成功标准。** 兴趣推送有用率（点「有用」或点击原链）≥ 40%；因兴趣推送触发「免打扰」的人数 ≤ 10%。

**打扰控制。** 工作日兴趣默认 0 或 1 条；周末可到 2 条。兴趣内容**禁止**写入工作晨报。

**失败降级。** 主题与画像弱相关则不推，宁缺。发布会未开始不剧透谣言。

### 4.3 场景 C｜轻陪伴：上下班与节奏（原始需求 4，P0）

**用户故事。** 上班有一条能决定今天先看什么的晨报；下班有一条能让我安心关机的收工。不要每天换着花样寒暄。

**触发条件。** 用户设定上下班时间（默认 09:10 / 18:40，可改）。支持「今天远程 / 今天请假」临时覆盖。

**输入。** 作息、时区、免打扰、昨日未读的「稍后」、今日关注源增量。

**输出形态。**

- 晨报：最多 3 条工作相关 + 0 条兴趣；每条一行结论 + 原链。
- 收工：今天你点过赞的卡片；1 件「明天必须看」；可选「本周已积 7 张卡片」。

**成功标准。** 晨报打开率 ≥ 60%；用户问卷「它让我更安心关机」≥ 50% 同意；主动闲聊轮次不作为成功指标。

**打扰控制。** 上下班各 1 条。迟到的晨报如果用户已在深度工作时窗，改投「稍后盒子」，不弹。

**失败降级。** 源全部失败则晨报改为：「今日源不可用。要不要手动给一个链接我帮你看。」禁止用空洞问候顶替。

### 4.4 场景 D｜交互提取画像（原始需求 2 前半，P0）

**用户故事。** 我不填长问卷。我加关注、点有用/无用、偶尔说「别推评测、我在做 Serving」，系统就应分开记工作和兴趣。

**触发条件。** 每次反馈、每次自然语言纠正、每次增删关注。

**输入。** 显式关注、按钮、短句纠正、可选技术栈（从模板勾选）。

**输出形态。** 用户可打开「我的画像」页：工作标签 / 兴趣标签分两栏，每条可删。秘书不在聊天里背诵画像。

**成功标准。** 第 7 天人均有效反馈 ≥ 5 次；工作标签被兴趣内容污染的人工抽检 ≤ 10%。

**打扰控制。** 不主动问「你还喜欢什么」超过每周 1 次。

**失败降级。** 抽不准就不写进画像，只记原始反馈事件。宁可画像瘦，不可脏。

### 4.5 场景 E｜工作文献检索与推送（原始需求 2 后半，P1）

**用户故事。** 我这周在做 Agent 记忆评测。秘书周三给我 1 篇和 LoCoMo / 长期记忆相关的论文或技术报告，而不是再推一篇 LLM 通识综述。

**触发条件。** 工作画像出现稳定项目关键词 ≥ 3 天；或用户说「帮我盯这个方向的论文」。频率默认每周 2–3 条，不每天。

**输入。** 工作画像、可选仓库主题、用户指定的会议/期刊/ArXiv 分类。

**输出形态。** 题名、一句话与当前工作的关系、方法/数据/开源情况三行、原链、PDF 链（如有）。不替用户下结论「这篇必读」，只说「相关点在哪」。

**成功标准。** 文献推送有用率 ≥ 35%；「和我当前工作有关」主观分 ≥ 3.5 / 5。

**打扰控制。** 不进休闲频道。可合并进周三或周五晨报。

**失败降级。** 检索为空则本周不推，并告诉用户「这周没找到高于阈值的，要不要放宽关键词」。禁止用热门论文凑数。

### 4.6 场景 F｜指定网站监测、习惯爬取、摘要与原链（原始需求 5 前半，P1）

**用户故事。** 我指定了团队常用的框架文档、内部技术博客（已授权）、某个产品更新页。页面更新后推摘要和原链。我常在周三晚上读长文，系统把习惯源的深度摘要放到那个时间。

**触发条件。** 用户提交 URL 并确认「允许监测」。变更检测发现正文/版本号/日期变化。习惯时段来自历史打开与「稍后」。

**输入。** URL、监测频率上限、是否允许正文抓取、所属工作/兴趣通道。

**输出形态。** 变更点列表（新增段落/版本号）+ 摘要 + 原链 + 抓取时间。不输出整页转载。

**成功标准。** 用户关心的更新漏报率 ≤ 10%（抽检）；无变更时零推送；礼貌爬取无投诉。

**打扰控制。** 每站点每天最多 1 次；小改动进周报。

**失败降级。** robots / 登录墙 / 反爬时停止抓正文，改为「页面有变化，请点原链」，并在 Web 页标记「仅监测到变更」。**禁止**建议绕过登录或未授权爬取。

### 4.7 场景 G｜点赞沉淀为知识库（原始需求 5 后半，P1）

**用户故事。** 我觉得这条摘要有用，点赞。它变成一张可检索卡片：标题、摘要、标签、原链、为何推荐、我的批注。两周后我问「上次那个评测集叫什么」，秘书能从库里答出来并给原链。

**触发条件。** 点「有用」或「收藏」；用户对卡片加批注。高置信自动入库仅作为阶段 B 末的对照实验。

**输入。** 原推送、用户标签修正、批注。

**输出形态。** 见第 7 节卡片结构。Web 个人主页是主阅读面；IM 只回链或三张卡片预览。

**成功标准。** 点赞到成卡成功率 100%（功能正确）；周复用（再次打开或被问答命中）≥ 25%；用户删除率 ≤ 15%。

**打扰控制。** 入库不发恭喜消息。每周五收工可提一句「本周新入 N 张」。

**失败降级。** 分类错了允许一键改类；摘要幻觉被用户标「不实」则卡片降权且不进推荐。

### 4.8 场景 H｜群消息读取与智能提醒（原始需求 1，P2）

**用户故事。** 我授权了「评测群」和「项目同步群」。有人 @我、提到我的服务名、或出现「今天 17:00 前提交」，即使我当时在开会，下班前也会收到一条摘要提醒，而不是群聊全文。

这是高价值高风险能力，必须满足下列约束才允许上线：

| 约束 | 规则 |
|---|---|
| 授权范围 | 用户主动拉机器人进群 + 在 Web 勾选白名单。未勾选的群，机器人在场也不读历史、不提醒 |
| 只提醒「和我相关」 | 默认规则：@我、我的姓名/花名、我订阅的项目关键词、我被指派的截止日期。纯闲聊、表情包、他人任务不提醒 |
| 免打扰时段 | 深度工作时窗与夜间，只写入「提醒盒子」，到收工或用户设定的「可打断」时再发 |
| 摘要而非原文搬运 | 提醒卡只含：谁、什么事、何时、原消息跳转链。不把群内容复制到其他群，不送公网模型 |
| 可审计 | 每次提醒记录：依据哪条规则、用了哪条消息 ID、是否已读。用户可一键「这类以后别提」 |
| 通道 | 仅官方机器人 API（飞书事件订阅等）。**禁止**客户端 hook、截屏 OCR、未授权导出 |

**触发条件。** 白名单群新消息命中相关度阈值，或用户设了定时（如每天 17:50「清一下今天和我有关的群待办」）。

**输入。** 官方回调的消息事件、用户关键词、组织通讯录中的显示名（需授权）。

**输出形态。** 「和你相关的 2 件事：1）… 2）…」+ 跳转。定时汇总优先于实时打断。

**成功标准。** 相关提醒准确率 ≥ 70%（用户标有关/无关）；漏掉 @我 的比例 ≤ 5%；因群提醒打开免打扰的比例 ≤ 15%。误报比漏报更伤信任，阈值从高往低调。

**打扰控制。** 默认「定时汇总」而非「条条实时」。实时只留给 @我和今天截止。

**失败降级。** 模型不确定是否相关 → 不推，记入审计「抑制」。API 权限被撤 → 立刻停止读取并私聊告知。

**会议 / deadline 抽取** 是该场景的子能力：只从已授权、已判定相关的消息里抽「时间 + 事项 + 责任人是否是我」。抽错的代价是用户关掉整个群能力，因此必须带「加入我的提醒 / 忽略」按钮，默认不写进系统日历，除非用户点确认。

## 5. 「EchoBot / AI 秘书」交互形态

### 5.1 人格与双声道

- **飞书声道：克制、专业、偶尔有温度。** 温度体现在记得节奏和用词准确，不体现在玩笑密度。超过 8 行必须折叠或改卡片。
- **桌面声道：短、有温度、可见状态。** 只说「今日 3 条在飞书」「正在整理」「升级了」。不主动闲聊，不讲段子。
- **不主动自称朋友，不道德绑架加班。** 升级演出不得出现在深度工作时窗。
- **说错就改。** 「这条不该归档，已撤销。」比道歉长文有用。

EchoBot 式人格是**外壳**：Roleplay 只驱动桌面姿态；Agent 才碰飞书、目标、记忆。皮肤不得改变推送配额、完成门闩、工作/兴趣隔离。

### 5.2 通道选择

**W0：飞书私聊机器人 + 桌面萌宠状态。** 极简 Web 个人主页可后置；来不及做 Web 就用飞书卡片完成设目标和画像查看。

| 通道 | 职责 | 不做 |
|---|---|---|
| 飞书机器人 | 今日目标、完成、归档预览、收工、按钮 | 写 PPT、管项目、群监听、知识库社交 feed |
| 桌面萌宠 | 未设 / 进行中 / 整理 / 升级姿态；一句状态 | 陪聊、独立推送通道、在深度工作弹气泡 |
| Web 个人主页（可后置） | 目标列表、画像两栏、知识库检索与改标签 | 团队广场 |

**为什么先选飞书，而不是企微或钉钉（对 AI 团队）：**

1. 交互卡片和按钮（有用 / 无用 / 稍后）是第一期画像的主输入，飞书卡片能力完整、文档清楚。
2. AI / 互联网团队飞书渗透率通常更高，试点不用先打「再装一个 IM」的组织战。
3. 飞书云文档/知识库以后若做团队库对接，路径短；但第一期**不依赖**这个对接。
4. 若试点团队实际只在企微：同一套内核换适配器，不换产品逻辑。方案不绑死飞书品牌，绑的是「IM 卡片 + 按钮反馈」。

钉钉作为第三备选：到达率可以，卡片与机器人事件模型对这种「个人秘书」不如飞书顺。

### 5.3 主动 vs 被动

| 类型 | 配额（工作日） | 例子 |
|---|---|---|
| 主动、定额 | 晨报 1 + 收工 1 + 兴趣 0–1 + 突发 0–1 | 版本更新、上下班 |
| 主动、抑制 | 相关但低优先级 | 进稍后盒子 |
| 被动、不限 | 用户提问、改关注、查知识库 | 「上周我收藏的评测集」 |

深度任务（比较两篇论文、总结一个站点的一周变更）只走对话，不主动开聊。

### 5.4 典型对话（按真实产品写）

**① 上班（W0 今日目标）**

> 秘书：今日 3 条，都从本周目标拆出来。  
> 1. 飞书测试卡能发到自己  
> 2. 目标数据模型落地

> 1. vLLM 0.x 发布，attention backend 有 breaking change → [Release]  
> 2. 你关注的评测仓库新增 baseline 脚本 → [PR]  
> 3. 云厂商推理档更新了限流说明 → [Changelog]  
> 为何推：你关注了 vLLM / 评测仓库；第 3 条与本周 Serving 标签匹配。  
> 〔有用〕〔无用〕〔稍后〕

**② 用户纠正通道**

> 用户：发布会别放早上。  
> 秘书：已把「发布会 / 现场演示」固定到兴趣频道，只在 12:00 后或下班后推。工作晨报不再出现。

> 用户：移。

**③ 文献（P1）**

**④ 收工**

## 6. 用户画像与推荐系统（创新研究点）

### 6.1 画像从哪来

| 信号 | 通道 | 强度 | 写入哪本画像 |
|---|---|---|---|
| 显式关注清单 | 用户 | 最强 | 用户指定工作或兴趣；默认工作 |
| 有用 / 无用 / 稍后 | 用户 | 强 | 随内容通道走；用户可改 |
| 阅读停留 / 是否点原链 | 隐式 | 中 | 只调排序，不写新标签（防误伤） |
| 自然语言纠正 | 用户 | 强 | 按句子意图分通道 |
| 工作仓库 / 技术栈（可选） | 用户授权 | 强 | 仅工作画像 |
| 作息与免打扰 | 用户 | 强 | 节奏档案，不是兴趣 |

对应到现有 `ProfileUpdate`：不要再往一个 `preferences` 里塞。建议在 metadata 层拆：

- `work_profile`：技术栈、项目词、文献偏好、工作源
- `interest_profile`：发布会、科技媒体、产品花絮
- `rhythm`：上下班、免打扰、稍后习惯
- `facts`：稳定事实（时区、角色、姓名）

VehicleMem 的单次抽取 Prompt 仍可用，但必须加硬规则：**一条记忆只能进入一个通道；不确定则不写入 preferences，只记 raw feedback。**

### 6.2 工作 / 兴趣隔离（硬约束）

污染的典型事故：用户晚上给发布会点了「有用」，第二天晨报出现「发布会花絮」。对策：

- 内容生产时打 `channel=work|interest`；
- 推送组装时工作槽位只读 work 源与 work 画像；
- 点赞默认强化**该条内容的通道**，不跨通道扩散标签；
- 每周抽检 20 条晨报，污染即 P0 缺陷。

这是本项目最重要的研究问题之一，见第 12 节。车载画像研究里兴趣与习惯混写是合理的；办公场景混写是产品事故。

### 6.3 冷启动：关注清单模板

用户安装后 2 分钟内必须能勾选，而不是面对空白：

| 模板组 | 示例（可增减） |
|---|---|
| LLM / 模型实验室 | OpenAI、Anthropic、Google DeepMind、国内头部实验室官方博客 |
| Agent | LangGraph、主流 Agent 运行时、内部 Agent 平台（若有授权源） |
| 评测 | ArXiv cs.AI / cs.CL、LM-Harness、内部评测仓库 Release |
| 开源框架 | vLLM、SGLang、PyTorch、Hugging Face Transformers |
| 云厂商 | 团队实际在用的那 1–2 家的 AI 产品 changelog |
| 论文源 | ArXiv 订阅类、Hugging Face Papers、指定会议页 |
| 兴趣（默认折叠） | 发布会日历、科技媒体 RSS；默认少勾，避免第一天变资讯 App |

第一期建议预置约 10 个默认可监测源（见第 13 节实验），用户取消比用户从零添加更容易。

### 6.4 推荐怎么排，不做成信息流

排序只用四列，不用深度兴趣网络：

1. 用户是否显式关注该对象  
2. 是否命中工作项目词  
3. 变更类型权重（安全 / breaking > 版本 > 博客）  
4. 近期同类反馈  

没有这些信号就**不推**。研究试点要的是可解释，不是 CTR 模型竞赛。

### 6.5 评价体系

| 指标 | 定义 | 第一期关注 |
|---|---|---|
| 推送有用率 | 有用 /（有用+无用），稍后不计入分母或单列 | 是 |
| 打扰投诉 | 免打扰开启、关键词「别推了」、卸载机器人 | 是 |
| 知识库复用率 | 本周被打开或被问答命中的卡片 / 库存卡片 | 阶段 B |
| 通道污染率 | 工作推送中实际为兴趣内容的比例 | 是 |
| 主动回馈率 | 见第 10 节北极星 | 是 |

## 7. 知识库设计

### 7.1 卡片结构

一张卡片就是一条可检索的 `MemoryItem` 特化，字段如下：

| 字段 | 说明 |
|---|---|
| title | 人读标题，优先用原文标题 |
| summary | 3–8 行，可被用户改 |
| category | 技术 / 产品 / 论文 / 发布会 / 踩坑 |
| tags | 用户可改；来自关注对象与抽取 |
| source_url | 必填 |
| why_recommended | 当时的可解释理由，入库后保留，便于研究 |
| user_note | 批注，可空 |
| channel | work / interest |
| source_type | rss / changelog / github / hf / arxiv / url / im |
| useful | 用户反馈 |
| created_at / updated_at | 时间 |
| memory_id | 对齐 VehicleMem `MemoryItem.id` |

禁止入库无 `source_url` 的模型自说自话。群提醒在 P2 若要入库，只存摘要 + 消息跳转，不存群原文。

### 7.2 自动分类

五类足够，第六类「其他」要每周清空。分类器可先用规则 + 小提示词：

- 论文：arXiv / 会议 / PDF  
- 技术：Release、API、框架、踩坑复盘  
- 产品：changelog、定价、功能上线  
- 发布会：Keynote、活动日程  
- 踩坑：用户批注含「坑 / 失败 / 不要用」或从内部复盘页来（需授权）

分错成本低于乱开 20 个标签。用户改类是强监督信号。

### 7.3 何时进库

| 动作 | 是否进库 | 阶段 |
|---|---|---|
| 点有用 | 是 | B 起；A 可先落「待入库队列」以免分散开发 |
| 手动收藏 | 是 | A 末若来得及，否则 B |
| 点无用 | 否，并作负例 | A |
| 稍后 | 否 | A |
| 高置信相关自动入库 | 默认关，对照实验用 | B 末 |
| 群消息 | 默认否，用户点「记下来」才入 | C |

阶段 A 若工程来不及做完整 Web 库，至少把点赞事件写入 VehicleMem 中期记忆，阶段 B 再物化成卡片。**不要为了「有知识库」在 A 阶段做一套独立 CMS。**

### 7.4 如何反哺推送与问答

- **推送：** 已入库卡片的 tags / 对象作为正例；用户改过的摘要里的否定句作为负例。
- **问答：** 先 search 个人库，再谈公网知识。回答必须能指回卡片与原链。
- **周报：** 周五按分类聚 5–10 张，形成「这周你实际吸收的」而不是「这周我推了什么」。

### 7.5 个人库 → 团队库的治理

团队库是垃圾堆的高发地。规则先行：

1. 默认私有。分享是显式动作，按单卡或按标签。  
2. 分享前必须有 `source_url` 和用户确认的摘要。  
3. 团队库要有退休：90 天无人打开且无人引用则下架到冷存。  
4. 禁止机器人把个人兴趣卡同步到团队。  
5. 阶段 C 才做；用 graphiti 做「论文–框架–项目」关系是可选项，不是门槛。

## 8. 信息获取与技术架构（研究级）

本节只到模块边界，不写实现说明书。

### 8.1 源

优先稳定、官方、可缓存的源：

- RSS / Atom  
- 官方 changelog / 博客  
- GitHub Releases 与指定 repo 的 Release 事件  
- Hugging Face papers / blog  
- ArXiv API（按分类与关键词，限频）  
- 会议与发布会日程页  
- 用户指定 URL（变更检测，不默认全站爬）

内部源必须走已授权的企业网络与账号，不写进公网提示词。

### 8.2 网站更新监测策略

1. 用户显式添加 URL，记录允许的抓取频率（默认 ≤ 每 6 小时，站点更严则更慢）。  
2. 遵守 robots.txt；尊重 `Retry-After`；统一 UA 与缓存。  
3. 先用条件请求（ETag / Last-Modified）或首页 hash；无变化不调用摘要模型。  
4. 有变化则抽正文diff 或主内容块，摘要只基于可见变更，并引用原链与抓取时间。  
5. 登录墙、验证码、明确禁止抓取的站点：停正文，只提示「疑似更新」。  
6. **禁止**未授权爬取、验证码破解、绕过付费墙。

### 8.3 群消息

只通过官方机器人 API。不做 IM 逆向、不做本地消息数据库偷读。群内容视为公司敏感数据：

- 推理默认走**私有化或内网模型**；
- 若必须用外部模型，先脱敏（去姓名、去项目暗号）且需安全评审，本试点默认**不允许**；
- 原始消息不落公网日志。

### 8.4 Agent 工作流

与主张中的内核一致，落成六步作业，每步可单独评测：

1. **感知：** 源轮询 / webhook /（P2）IM 事件  
2. **过滤：** 通道、变更类型、相关度、配额、免打扰  
3. **摘要：** 短摘要 + 变更点；不确定则降级为标题+原链  
4. **个性化：** 双画像与可解释理由  
5. **推送：** 飞书卡片  
6. **反馈：** 按钮与纠正 → VehicleMem `add` → 更新 work/interest profile  

记忆写入对齐现有接口：业务只调 `create_memory()`，用 hybrid 模式——端侧或内网先行，云端可选。公司团队默认 **edge 或私有 cloud**，不默认公有云记忆。

### 8.5 隐私与部署

| 选项 | 适用 | 备注 |
|---|---|---|
| 全内网 edge | 最敏感试点 | 对齐 VehicleMem edge：本地向量 + 本地画像 |
| 私有 cloud | 小组共用一台服务 | 对齐 cloud 模式，鉴权已有雏形 |
| hybrid | 笔记本客户端 + 内网服务 | 有 outbox，适合笔记本休眠 |

画像与知识库按 `user_id` 隔离。管理员不可默认浏览个人兴趣库。

### 8.6 明确禁止

- 未授权爬取、未授权监听群、客户端 hook  
- 把群内容、内部文档发送到公网模型  
- 无白名单的「全公司群监听」  
- 用陪伴话术收集与工作无关的私生活并写入工作画像  
- 写 PPT、虚拟电脑、浏览器代操作、Jira/日历自动建任务  
- 未勾完成或未经确认就自动建库  
- 靠换皮肤跳过 Lv3 / Lv5 门闩

## 9. 分期计划与组织方式

研究试点按 **W0 + 12–16 周** 切四段。人力按小研究组假设：**产品研究 1 + 后端/Agent 2 + 前端（Web+飞书卡片+桌面宠）1，兼做评测。** W0 可以先自己当唯一用户。

### 阶段总览

| 阶段 | 周次 | 目标 | 范围 | 成功标准 | 主要风险 |
|---|---|---|---|---|---|
| W0 目标闭环 | 第 0 周（8/24–8/30） | 自己每天用目标卡；秘书升到 Lv2 | 周/日目标、完成、归档预览、配额、桌面姿态 | 完成→成卡 ≥ 3；撤销率 < 30%；工作时零弹窗；愿下周继续 | 做成待办 App；整理幻觉；升级打断工作 |
| A 个人兴趣秘书试点 | W1–W6（**Lv3**） | 5–15 人每天愿意看晨报 | 关注清单、更新监测、兴趣推送、上下班、反馈按钮、画像两栏雏形 | 周活跃且主动回馈 ≥ 40%；有用率 ≥ 35%；污染率 ≤ 10%；无合规事故 | 源不稳定；推太多；做成资讯 Bot |
| B 工作提效 | W7–W11（**Lv4**） | 文献 + 习惯源 + 知识库开始反哺 | 文献推送、指定 URL 监测、点赞成卡、Web 检索、问答打到个人库 | 文献有用率 ≥ 35%；库周复用 ≥ 25%；「愿意继续用」≥ 70% | 文献乱推；库变收藏垃圾 |
| C 群提醒 + 部门推广 | W12–W16（**Lv5**） | 在信任基础上加群能力 | 白名单群、相关度提醒、deadline 确认、可选团队分享 | 群提醒准确率 ≥ 70%；扩到 1 个相邻组仍不炸免打扰 | 隐私评审、误报、部门差异 |

W0 不过线（完成→成卡 < 3，或撤销率 ≥ 30%，或不愿继续），**停止加功能**，重复目标闭环，不进入关注源。阶段 A 有用率低于 25% 或免打扰率高于 30%，同样先修相关性，不进入 B。

### 阶段 W0（8/24–8/30）细节

- 周一：`secretary` 包、飞书私聊测试卡、WeeklyGoal / DailyGoal / CompletionEvent（各 ≤ 3）。  
- 周二：飞书上设周/日目标，按钮完成 / 改一下 / 明天；收工只问一次。  
- 周三：完成事件写入 VehicleMem，`channel=work`。  
- 周四：完成门闩 + 归档预览确认；无 `source_url` 不成卡。  
- 周五：桌面宠姿态；达标则 Lv1→Lv2；升级只在收工窗口。  
- 周六：自己当种子用户跑一天，记录打扰与整理事故。  
- 周日：秘书生成 W0 周报；过线才把关注源列为 Lv3。

代码放在 `company_agent/secretary/`，不在 EchoBot-main 里改办公逻辑。EchoBot 只当 pet runtime 依赖。

### 阶段 A（W1–W6）细节

- W1：飞书机器人骨架、关注模板、10 个默认源、有用/无用/稍后、作息设置。  
- W2：5 人封闭实验（见第 13 节）。  
- W3–W4：扩到 10–15 人；双画像隔离；Web 上看关注与画像。  
- W5–W6：稳定性、配额策略实验（每天 2 条 vs 3 条）、写阶段 A 报告。

### 阶段 B（W7–W11）细节

- 文献：ArXiv / HF Papers + 工作画像，每周 2–3 条。  
- 习惯源：用户指定 URL 的变更检测与摘要。  
- 知识库：卡片物化、分类、周五周报、问答检索。  
- 对照实验：自动入库开/关对复用率的影响。

### 阶段 C（W12–W16）细节

- 安全评审通过后，才读白名单群。  
- 默认定时汇总，实时仅 @与当天截止。  
- 选 1 个相邻业务组用「换模板不换内核」的方式试推广。  
- 团队库只开「自愿分享」，不开自动同步。

### 组织方式

- 双周评审只看：有用率、免打扰、污染率、2 个用户原话。不看推送条数。  
- 种子用户有否决权：3 人以上说「比不用更烦」，当周必须减配额。  
- 研究记录与产品迭代同一仓库：评测集用真实推送与反馈，不要只用公开 QA 集冒充成功。

## 10. 衡量指标

### 10.1 北极星

**周活跃且「主动回馈」的用户占比。**

- 周活跃：7 天内打开过至少 1 条推送或访问 Web。  
- 主动回馈：点赞 / 无用 / 收藏 / 纠正 / 增删关注。只读不点的人算弱活跃，不算北极星分子。

理由：推送条数、DAU 都可以靠多推刷出来；愿意纠正系统的用户，才是秘书关系成立的证据。

目标（阶段 A 结束，N≈10–15）：北极星 ≥ 40%。低于 25% 视为产品方向未成立。

### 10.2 配套指标

| 指标 | 计算 | 阶段 A 参考线 | 警戒线 |
|---|---|---|---|
| 打开率 | 打开或点击原链 / 推送条数 | ≥ 50% | < 30% |
| 有用率 | 有用 /（有用+无用） | ≥ 35% | < 20% |
| 免打扰触发 | 新开免打扰或「别推了」人数 / 周活 | ≤ 15% | > 30% |
| 通道污染率 | 抽检晨报中的兴趣内容 | ≤ 10% | > 20% |
| 知识库周复用 | 命中或打开的卡片 / 有库存的用户 | 阶段 B ≥ 25% | < 10% 且库存仍在涨 |
| 主观「愿意明天继续用」 | 双周一问，5 分制选 4–5 的比例 | ≥ 60% | < 40% |
| 节省时间自评 | 分钟/周，仅作参考 | 先收集分布，不设 KPI | 出现大量「浪费时间」 |

不把「对话轮次」「人格好感」设成主 KPI，避免产品滑向陪聊。

## 11. 风险与伦理

| 风险 | 可能怎么发生 | 对策 |
|---|---|---|
| 打扰 | 源一多就连发；突发定义过宽 | 硬配额；突发白名单；用户一键今日静音 |
| 幻觉摘要 | 把「计划支持」写成「已发布」 | 变更点尽量摘原句；不确定标待确认；无正文则不摘要；用户标「不实」降权 |
| 版权 | 整页转载、论文全文进库 | 只存摘要与链接；不提供全文镜像；内部文档按权限 |
| 隐私 | 群内容、个人兴趣进公网或进团队 | 私有化优先；群默认不入团队库；双画像隔离；审计日志 |
| 过度陪伴依赖 | 用户把情绪安抚当需求 | 不做情感咨询；下班不挽留；人格皮肤可关 |
| aily 覆盖幻觉 | 用户认为「这不就是飞书 AI」 | 标准回答：他们做新的，我们守节奏、记住你做完的；W0 不做写 PPT / 虚拟电脑 |
| 桌宠三周新鲜感 | 升级只换外观 | 升级必须解锁真能力；W0 的 Lv2 = 完成后整理 |
| 目标变成待办 App | 超过 3 条或开始催办 | 硬上限 3；催办占用晨报/收工，不另开通道 |
| 整理幻觉 | 归错文档 | 预览确认、可撤销、无原链不成卡 |
| 信息茧房 | 只推已点赞的窄标签 | 每周允许 1 条「相邻但未关注」且必须标明探索；用户可关；工作频道禁止用茧房当理由堆资讯 |

另外两条研究伦理：

- 种子用户必须知情：记了哪些字段、群开没开、数据存在哪。  
- 评测数据若含群消息，不得带出公司。

## 12. 创新研究命题

本题作为「个人助理创新研究」立项，除产品交付外，应能回答下列问题。每题都要有数据，不接受事后叙事。

1. **工作 / 兴趣双画像如何避免互相污染？**  
   指标：污染率、用户纠正次数、隔离规则开/关对照。工作区现有 profile 是单本的，本题提供办公场景的改造依据。

2. **主动推送的最佳打扰预算是多少？**  
   实验：同一用户群随机或轮转「每天 2 条 / 3 条 / 5 条」。看北极星、免打扰、有用率。预期：超过 3 条后有用率下降、免打扰上升。

3. **「点赞沉淀」能否形成比聊天记录更可用的个人知识？**  
   对照：仅聊天记忆 vs 卡片库。任务：两周后找回「当时那条 breaking change」。看成功率与时间。

4. **陪伴型人格对办公工具留存的真实贡献是什么？**  
   对照：纯通知卡 vs 秘书短句（上下班）。若留存无显著差异，阶段 B 起削弱人格，把预算给相关性。

5. **群消息提醒的相关度阈值应设在哪？**  
   ROC：@我、关键词、模型打分的组合。优先压误报。没有 ≥70% 准确率不开实时。

6. **（可选）习惯时段爬取是否比固定晨报更省打扰？**  
   把深度摘要从早 9 点改到用户历史「稍后」时段，看打开率与免打扰。

这些问题构成研究产出：不止一份 Bot，而是一组可发表或可内部复用的结论（打扰预算、双画像、点赞进库是否优于会话记忆）。

## 13. 结论与立刻可做的 W0

### 13.1 结论

对工位上的自己（以及之后的 AI 开发小组），正确的第一期不是「能读群的全能办公机器人」，也不是更弱的飞书 aily，而是：

- 用极窄的周/日目标证明「我能守」；  
- 用完成即归档证明「做完有下落」；  
- 用 Lv1→Lv2 把分期做成成长，而不是功能堆砌；  
- 关注源晨报锁 Lv3，群提醒锁 Lv5；  
- 记忆层复用 VehicleMem / MemoryOS，产品层只创新「双通道 + 配额 + 进库门闩 + 升级」。

喜欢用，来自「每天想打开、白天不被吵、做完能翻出来」。aily 帮你做新的；我们帮你守节奏、记住你做完的。

对外三个词：**专属、少扰、能记。** 形态：**萌宠、飞书。** 机制：**完成即归档、升级即解锁。**

### 13.2 W0 实验（8/24–8/30，取代原「两周资讯晨报」作为第一道门）

**目的。** 用最小系统验证：目标打不打得开、完成会不会归档、升级会不会让人多点而不是多吵。不验证群、不验证关注源、不验证文献、不写 PPT。

**对象。** 先自己。过线后再 5 人。

**通道。** 飞书私聊卡片 + 桌面宠姿态（宠可以并行，但不得阻塞卡片闭环）。

**每日动作。**

- 09:10 ±10 分钟：1 条今日目标卡（0–3 条），按钮完成 / 改一下 / 明天。  
- 勾完成：出归档预览，确认才入库。没有材料就明确说没有，不准空编。  
- 18:40：收工只问一次未完成；达标周五才升级。  
- 不做群读取。不做主动闲聊。不做资讯凑数。

**通过 / 不通过。** 通过：完成→成卡 ≥ 3，撤销率 < 30%，工作时零弹窗，自己愿下周继续。不通过：减目标条数、收窄授权范围，**加功能不算复盘。**

**通过后的唯一允许增量。** 开 Lv3 关注源实验（原 §13.2 两周资讯设计，下移为 Lv3 门闩）。不通过则重复 W0。

### 13.3 Lv3 两周实验设计（原 W1–W2，仅 W0 过线后执行）

**目的。** 飞书通道是否被打开；双通道配额是否可执行；有用/无用是否收集得动。不验证群、不验证知识库完整 UI、不验证文献算法。

**对象。** 5 个种子用户，均来自 AI 开发小组，覆盖至少 1 名研究、1 名工程、1 名应用。本人知情同意。

**通道。** 只做飞书私聊机器人 + 一个表格或极简页用来勾选关注（来不及做 Web 就用飞书表单）。

**默认 10 个源（可按团队替换，但必须工作/兴趣分开）：**

| # | 源 | 通道 |
|---|---|---|
| 1 | vLLM GitHub Releases | 工作 |
| 2 | 团队常用的第二个推理/训练框架 Release | 工作 |
| 3 | Hugging Face Blog 或 Papers 日更 | 工作 |
| 4 | ArXiv cs.CL 或 cs.AI（关键词过滤，不是全量） | 工作 |
| 5 | 团队在用的云厂商 AI changelog | 工作 |
| 6 | PyTorch 或 Transformers Release | 工作 |
| 7 | 国内一源科技媒体 RSS（机器之心或等价） | 兴趣 |
| 8 | 一个国际科技媒体 AI 栏目 RSS | 兴趣 |
| 9 | NVIDIA 或 Google 或 Apple 的新闻/活动页（选团队更可能看的一个） | 兴趣 |
| 10 | 一个指定产品更新页（如某开源 Agent 框架 changelog） | 工作或兴趣，由用户自选 |

**每日动作。**

- 09:10 ±10 分钟：1 条工作晨报（0–3 条子项）。  
- 12:30 或 19:00（用户选一个休闲窗）：1 条兴趣。若当日兴趣源无更新，明确说「今天没有新的」，**不要用旧闻或热榜凑数**。  
- 每条带原链和「有用 / 无用 / 稍后」。  
- 不做群读取。不做主动闲聊。用户问了再答。

**数据。** 逐条记录：用户、通道、源、是否打开、按钮、是否抱怨、是否改关注。第 7 天和第 14 天各问三句：愿不愿意明天继续用；哪条最有用；哪条最烦。

**预期学习（两周后必须能回答）：**

1. 5 人里有几人还在看晨报？若 < 3，问题在源或摘要，不在「功能不够」。  
2. 有用率是否稳定在 30% 以上？兴趣和工作哪边更撑日活？  
3. 「今天没有新的」是否比硬凑更被接受？  
4. 按钮反馈够不够训画像，要不要加一句自然语言纠正引导？  
5. 飞书卡片是否足够，还是必须立刻做 Web？

**通过 / 不通过。** 通过：≥3 人表示愿意继续，且免打扰 < 2 人，且没有把兴趣打进晨报的事故。不通过：减源、减配额、重写摘要规则，**加功能不算复盘。**

**两周后的唯一允许增量。** 通过则开阶段 A 余下四周（扩人、画像页、节奏微调）。不通过则重复 2 周实验，换源或换摘要，不进入文献与群。
